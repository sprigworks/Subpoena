# Level 3: one platform contract, two service teams

Run from the repository root with Go 1.25+ and Linux `/proc` available. The
root `make check` runs this target too, so it also needs Linux `/proc`. Under
`make SANDBOX=1` the target is skipped, because the example's modules resolve
through the module proxy:

```sh
make platform
```

This runs the full shared-module suite, then each service's race-enabled tests,
lint and cross-examination. It needs neither Docker nor a collector. Each test
runs one action at a time; the allowed command sleeps for 0.2 seconds so the
polling process witness can see it. This is a runnable ownership example, not
an enterprise deployment stack.

| Module | Owner's responsibility | Gate |
| --- | --- | --- |
| `shared` (`example.com/platform/contract`) | Registry, generated constants, embedded invariant, production exporter policy, generated Grafana rules | `platform-contract` CI job |
| `services/build` | Reject an untrusted build requesting secrets; other builds may execute | `platform-service (build)` CI job |
| `services/deploy` | Reject a production deployment without approval; other deployments may execute | `platform-service (deploy)` CI job |

Both services require contract **v0.1.0** in their own `go.mod`. Local `replace`
directives make the example runnable inside this checkout; this module has not
been published. In a real organization, publish the shared module under an
organization-owned path and tag it, require that version in each service, and
remove the local replacements. Pin Subpoena to a released version too. There
is no `go.work` joining the services, so one module's tests cannot silently
stand in for another's.

The platform team owns the vocabulary and invariant; each service team owns
its policy, instrumentation, witness tests and upgrade timing. The repository's
CODEOWNERS uses its current human owner as the platform-team stand-in for
`shared/`. Replace that handle with your own team when adopting this layout.

## What CI checks

- Weaver 0.28.0 validates the shared registry and regenerates its constants.
  `go generate ./invariants` regenerates invariant names. `make check-generated`
  rejects differences in committed constants, names and alert provisioning.
- Each service emits only shared generated names. Its lint command passes
  `-registry` and `-invariants` explicitly because the contract is imported from
  another module. Dead-telemetry lint applies to the complete service.
- Both services test all four policy input combinations. Each denial checks
  stopped-witness health and process absence, the recorded denial, and the
  shared invariant. Allowed controls must be observed by the witness.
  `WatchSpawns` also checks at cleanup after an earlier assertion fails.
- Each service marks its authorization return as an enforcement statement.
  Cross-examination requires a green baseline and removes that return; a
  surviving or non-compiling mutant fails the service's CI gate. Cross only
  removes the return. Mutants of the condition or the policy itself (an
  inverted check, a wrong rule) are caught by the policy-combination tests in
  `go test`, not by cross.
- Service tests attach `telemetry.ProductionExporter` to the harness provider's
  export path. They verify the raw test capture retains action ID, the
  production export drops it, and the authorization decision remains.
  Use this same wrapper around the actual service exporter in production.
- The repository's `registry.yml` workflow diffs only the root `registry/`, so
  `shared/registry` gets no `weaver registry diff` or breaking-change label. Its
  gate is CODEOWNERS review of `shared/` plus each service's CI job, which
  fails if a contract change breaks that service.
- `shared/telemetry/production.go` has no test of its own; the service jobs'
  production-export checks are what exercise it.
- `shared/alerts/rules.yaml` is generated by `go run ./cmd/platform-generate`
  from the embedded invariant. Tests require the exact invariant text plus
  `| count_over_time()`, a separate telemetry-liveness rule, and production-safe
  tiers for every attribute the invariant reads.

The checked-in provisioning targets a Tempo datasource with UID `tempo` and
uses the gateway example's instant-query, reduce, threshold pattern. The shared
rule evaluates both services' application spans. Its liveness rule detects no
authorization telemetry across that datasource; it cannot tell you whether
one service stopped reporting while the other stayed active. Scope provisioning
and liveness to your deployed service boundaries before using it operationally.
These checks validate generation and query contracts; this example does not run
Grafana's scheduler or deploy a kernel witness. The gateway's separate
[`make alerts`](../../Makefile) target exercises its own rules against live
Grafana. Tier 3 observes application testimony; it cannot prove process absence.

ProcWitness uses best-effort `/proc` polling and falls back to lineage without
a session cgroup. Healthy capture does not eliminate the possibility of missing
a short-lived process. See [witness limitations](../../witnesses/README.md).

## Rolling out a new invariant

1. The platform team reviews a contract change separately from a service fix.
   Add vocabulary deliberately, annotate export tiers, and write the invariant
   in `shared/invariants`. Keep old names while older service versions use them.
2. With Weaver installed, run `make -C shared generate` and `make check` here.
   Review generated constants and alert queries; CI checks they stay current.
   A production invariant must read only attributes retained by the exporter.
3. Publish a new shared-module version. Each service team upgrades its explicit
   requirement, updates instrumentation and tests, and runs its own `make check`.
   A service has adopted an invariant only when its denied and allowed controls
   and enforcement mutants pass; a dependency bump alone is insufficient.
4. After the services emit the new contract, review and provision the generated
   rules into the intended Tempo/Grafana environment. Validate the scheduler,
   traffic liveness and any independent witness there. Remove old contract
   entries only after consumers and deployed rules have migrated.

Generation is automatic; publishing, service upgrades and production rollout
remain reviewed team actions. The example makes no claim to automate those steps.
